# Zone-Align AI

Zone 2 심박수 트레이닝 + 식단 기록 앱. 정적 프론트엔드(`index.html`) + 음식 사진 분석/영양정보 조회를 대신 처리하는 서버리스 함수 두 개(`api/analyze-food.js`, `api/nutrition-info.js`)로 구성되어 있으며, Vercel에 그대로 배포할 수 있습니다.

## 구조

```
.
├── index.html               # 프론트엔드 전체 (단일 파일)
├── breathing-engine.js      # 호흡 마이크 분석 엔진 (장치 프로필/보정/신호 품질/검증 통계)
├── api/
│   ├── analyze-food.js      # 음식 사진 분석 (Gemini, GEMINI_API_KEY)
│   └── nutrition-info.js    # 음식 이름으로 영양정보 조회 (NUTRITION_API_KEY)
├── tests/
│   ├── breathing-engine.test.js        # `npm test`로 실행 (Node)
│   ├── breathing-engine.tests.core.js  # 실제 테스트 본문 (Node/브라우저 공용)
│   ├── run-tests.html                  # Node 없이 브라우저에서 같은 테스트를 돌리는 러너
│   └── sample-validation-data.json     # 검증 모드 파일 형식을 보여주는 합성 예시 데이터
├── .env.example
├── package.json
├── vercel.json
└── README.md
```

`GEMINI_API_KEY`는 오직 `api/analyze-food.js`가, `NUTRITION_API_KEY`는 오직 `api/nutrition-info.js`가 각각 `process.env`로만 읽습니다. `index.html`을 포함해 브라우저로 전송되는 어떤 코드에도 두 키 중 어느 것도 포함되어 있지 않습니다. 두 기능을 서로 다른 키/env 변수로 분리해둔 이유는 아래 "영양정보 API 설정" 참고.

## 배포 순서 (Vercel)

1. 이 폴더(`index.html`, `api/`, `package.json`, `vercel.json`)를 그대로 Git 저장소(예: GitHub)에 올립니다.
2. [vercel.com](https://vercel.com)에서 New Project → 방금 만든 저장소를 선택해 Import 합니다. 별도 빌드 설정은 필요 없습니다(Framework Preset: Other로 두면 됩니다).
3. **배포 전에** Vercel 프로젝트 설정 → **Settings → Environment Variables**로 이동해 아래 두 값을 추가합니다.
   - Key: `GEMINI_API_KEY` / Value: 발급받은 실제 Gemini API 키 (Google AI Studio에서 발급) - 음식 사진 분석에 사용
   - Key: `NUTRITION_API_KEY` / Value: 영양정보 조회에 사용할 API 키 (자세한 내용은 아래 "영양정보 API 설정" 참고)
   - Environment: 두 값 모두 Production / Preview / Development 체크
   - 저장 후 **Deploy**(또는 이미 배포된 경우 **Redeploy**)를 눌러야 환경변수가 함수에 반영됩니다.
4. 배포가 끝나면 `https://<your-project>.vercel.app`으로 접속해 앱이 뜨는지 확인합니다.
5. 음식 사진 촬영 화면과 음식 검색 화면에서 각각 정상적으로 결과가 나오면 설정이 끝난 것입니다.


**주의: `.env.local` 파일은 절대 Git에 커밋하지 마세요.** (`.gitignore`에 이미 포함되어 있다면 그대로 두고, 없다면 `.env*.local` 한 줄을 추가하세요.)

### 이미 GitHub Pages에 올려둔 프론트엔드를 계속 쓰고 싶다면

`api/` 폴더(두 함수 모두)만 별도로 Vercel에 배포하고, GitHub Pages의 `index.html`이 `https://<your-project>.vercel.app/api/analyze-food`와 `/api/nutrition-info`로 요청하도록 두 `fetch(...)` 호출부의 경로를 절대경로로 바꿔주면 됩니다(현재는 같은 도메인에서 서비스한다는 가정하에 상대경로로 되어 있습니다). 이 경우 Vercel 쪽 **Environment Variables**에 `ALLOWED_ORIGIN`을 GitHub Pages 도메인(예: `https://shfkszldnl33-web.github.io`)으로 설정해 CORS를 그 도메인으로만 제한하는 것을 권장합니다. 값을 비워두거나 `*`로 두면 모든 도메인에서의 호출을 허용합니다(기본값).

## PWA 캐시 버전 관리 (중요 - 배포할 때마다 확인)

이 앱은 `service-worker.js`가 `index.html`/`breathing-engine.js`를 **캐시 우선(cache-first)** 으로 서빙하는 PWA입니다. 브라우저는 `service-worker.js` **파일 자체의 바이트가 바뀌어야만** 새 버전이 있다는 걸 감지합니다.

**`index.html`이나 `breathing-engine.js`를 고칠 때마다, `service-worker.js`의 `CACHE_NAME`도 반드시 같이 올리세요** (`zone-align-ai-v1` → `v2` → `v3` ...). `CACHE_NAME`을 안 올리면:

- 브라우저가 업데이트 자체를 감지하지 못해 `index.html` 안의 "새 버전이 준비됐어요" 배너가 영영 뜨지 않고,
- 이미 한 번이라도 앱을 열어본 사용자는 아무리 새 코드를 배포해도 **캐시에 저장된 예전 버전**을 계속 보게 됩니다.

2026-09-16에 정확히 이 문제로 메트로놈/Zone 2 측정/상세 신호 정보 패널이 "고장 난 것처럼" 보였던 적이 있습니다 (실제 코드는 정상이었고, 원인은 `CACHE_NAME`이 초기 커밋 이후 한 번도 안 올라간 것). 그때 `v1` → `v2`로 올려서 해결했습니다.

## 영양정보 API 설정

`api/nutrition-info.js`는 음식 검색 화면(직접 이름을 입력해 영양정보를 찾는 기능)에서 사용하는 별도의 서버리스 함수입니다. 요청받은 대로 API 키를 **`NUTRITION_API_KEY`라는 별도의 환경변수**로 읽으며, 코드 어디에도 키 값 자체는 적혀 있지 않습니다.

- **현재 연동된 제공자**: 이 프로젝트에 이미 있는 Gemini API를 그대로 사용합니다 - `GEMINI_API_KEY`와 같은 서비스(Google Gemini)이지만, **별도의 키/환경변수로 분리**해두었습니다. 그래서 두 기능(사진 분석 vs. 이름으로 영양정보 조회)의 키를 서로 다른 시점에 발급/교체/제한(rate limit)해도 서로 영향을 주지 않습니다. 두 변수에 같은 키 값을 넣어도 되고, 다른 키를 넣어도 됩니다.
- **키 발급**: [Google AI Studio](https://aistudio.google.com/app/apikey)에서 API 키를 발급받으세요 (Gemini용 키 발급과 동일한 절차입니다).
- **설정 방법**:
  - Vercel 배포: Project Settings → Environment Variables → `NUTRITION_API_KEY` 추가 → Redeploy.
  - 로컬 개발: `.env.example`을 `.env.local`로 복사한 뒤 `NUTRITION_API_KEY=` 뒤에 키를 채워 넣기.
- **다른 전용 영양정보 DB API로 바꾸고 싶다면**: `api/nutrition-info.js`의 `buildNutritionPrompt()`와 `callNutritionProvider()` 두 함수만 그 API의 요청 형식에 맞게 바꾸면 됩니다. 요청/응답 형식(`POST { query }` → `{ ok, food: { name, baseAmount, unit, kcal, protein, carbs, fat, sugar, sodium, desc } }`), 환경변수 이름(`NUTRITION_API_KEY`), 에러 처리 방식은 그대로 유지하면 `index.html` 쪽은 전혀 손댈 필요가 없습니다.

## 이번 개편에서 바뀐 점

- **Gemini API 호출은 이제 서버(`api/analyze-food.js`, `api/nutrition-info.js`)에서만 실행됩니다.** 프론트엔드가 Google API를 직접 호출하던 코드(음식 사진 분석, 텍스트 검색, DTT 운동 중 음성 정밀분석)를 모두 제거했습니다.
- **개인 API 키를 입력하던 설정 화면, 저장 버튼, 발급 안내 문구를 모두 제거**했습니다. 방문자는 키를 몰라도 되고, 볼 수도, 저장할 수도 없습니다.
- 프론트엔드는 사진 분석은 `POST /api/analyze-food`(`{ imageBase64, mimeType }`), 텍스트 기반 영양정보 검색은 `POST /api/nutrition-info`(`{ query }`)로 - 서로 다른 주소와 서로 다른 API 키(`GEMINI_API_KEY` / `NUTRITION_API_KEY`)를 사용해 요청합니다.
- API 오류가 발생해도 화면에는 항상 "잠시 후 다시 시도해주세요" 같은 일반적인 문구만 표시됩니다. 실제 오류 메시지나 키 정보는 절대 화면에 노출되지 않고, Vercel 함수 로그(서버 쪽)에만 남습니다.
- CORS 프리플라이트(OPTIONS)와 잘못된 요청(빈 body, 잘못된 이미지 형식, 너무 큰 사진, 허용되지 않는 메서드 등)에 대한 처리가 두 서버리스 함수 모두에 포함되어 있습니다.
- 이름 입력란은 선택 사항으로 남겨두었고(인사말 표시용, 이 기기 브라우저에만 저장, 서버로 전송되지 않음), **전화번호 입력란은 완전히 제거**했습니다. 애초에 실제 로그인/인증 서버가 없는 앱이라 전화번호를 수집할 이유가 없었습니다.
- 심박수 운동 기록, 식단 기록, Zone 2 목표 계산, Talk Test 등 기존 기능은 서버 유무와 무관하게 그대로 동작합니다. Gemini 서버가 아직 설정되지 않았거나 일시적으로 응답하지 않을 때는, 사진 분석만 기기 내장 AI(지원 브라우저) → 자체 인식 모델(TF.js) 순서로 자동으로 대체됩니다.

## 호흡 마이크 분석 - 장치별 보정, 신호 품질, 그리고 한계

`breathing-engine.js`가 이어폰/헤드셋/휴대폰 마이크로 측정한 호흡 신호를 처리하는 모듈이고, `index.html`의 `startBreathingAnalysis()`가 이를 Web Audio 파이프라인과 연결합니다. 테스트는 `tests/`에 있습니다.

### 왜 이 구조로 바꿨나

기존 방식은 마이크의 **음량(RMS)만으로** 호흡 피크를 판정했습니다. 그런데 줄 이어폰/무선 이어폰/헤드셋/휴대폰은 마이크와 입 사이 거리가 서로 다르고, 같은 기기라도 사람마다 호흡 세기가 다르며, OS의 자동 이득 조절(AGC)이 그 차이를 다시 한번 왜곡합니다. 그 결과 "마이크가 멀어서 신호가 약함"과 "실제로 숨을 얕게 쉼"을 음량만으로는 구분할 수 없었고, 러닝 중 발소리·케이블 흔들림·바람 소리·주변 소음·말소리·클리핑이 전부 그대로 "호흡"으로 오인될 수 있었습니다.

### 장치 유형 선택과 초기 프로필

앱 시작(회원가입) 화면과 운동 화면에서 **줄 이어폰 / 무선 이어폰 / 헤드셋 / 휴대폰 마이크** 중 하나를 고릅니다. 이 선택은 `breathing-engine.js`의 `DEVICE_PROFILES`에 있는 기본값(감지 임계값, 노이즈 플로어 반응 속도 등)을 불러오는 **출발점**일 뿐입니다.

**중요: `DEVICE_PROFILES`에 적힌 `assumedMouthDistanceCm`(예: 줄 이어폰 15cm, 무선 이어폰 25cm, 헤드셋 8cm, 휴대폰 35cm) 같은 수치는 의학적으로 검증되었거나 실측된 값이 아니라, 방향성만 맞춘 초기 공학적 설정값(engineering starting values)입니다.** 실제 사용자 데이터로 검증되지 않았고, 검증되기 전까지는 "정확한 거리"라고 표현하지 않습니다. 코드 주석에도 동일하게 명시되어 있습니다.

### 마이크-입 거리를 앱이 직접 잴 수 없는 이유

스마트폰/이어폰은 마이크와 입 사이의 물리적 거리를 측정할 방법이 없습니다. 소리 크기만으로 거리를 역산하려면 (1) 마이크 자동 이득 조절이 만드는 음량 보정, (2) 사람마다 다른 호흡 세기 차이를 모두 알아야 하는데, 이 앱은 그 두 값을 분리해서 알 수 없습니다. 그래서 이 앱은 "거리를 측정한다"고 주장하지 않고, 대신 **세션 시작 시 5초간 그 사람·그 기기의 실제 신호를 재서(아래 "5초 보정" 참고) 그 세션에 맞게 정규화**하는 방식을 씁니다. 이 정규화 값(`normalizationGain`)도 세션마다 다시 계산되는 상대적 보정값이지, 절대적인 거리나 음량 기준이 아닙니다.

### 5초 보정 (세션 시작 시 1회)

운동을 시작하면 5초간 평소처럼 호흡하도록 안내하고, 그동안 다음을 측정합니다 (`createCalibrator()` 참고):

- 주변 소음 RMS/에너지 (가장 조용한 구간 20%의 평균)
- 평균 호흡 신호 크기, 신호 표준편차
- 신호 대 잡음비(SNR)
- clipping 비율
- 호흡 이벤트 후보의 평균 크기와 후보 간 시간 간격

이 값들로 "이 기기+이 사람"에 맞춘 정규화 계수와 임계값을 만들고, 후보 이벤트 간격은 개인 안정 시 호흡수 기준선으로도 재사용됩니다(기존에 있던 별도의 30초 기준선 측정을 대체합니다).

### 거리 보정은 어디에 쓰이나 (Zone을 직접 바꾸지 않음)

정규화된 음량은 **호흡 이벤트를 검출할지 말지 판단하는 임계값**과 **신호 품질 점수**를 계산하는 데만 쓰입니다. 호흡수(분당 호흡 횟수) 자체는 항상 **검출된 호흡 이벤트 사이의 시간 간격**으로만 계산되며(`computeBreathsPerMinute()`), 음량 값이 직접 호흡수나 Zone 계산식에 들어가지 않습니다. 따라서 마이크가 가깝든 멀든, 일단 호흡 이벤트가 올바르게 검출되기만 하면 같은 호흡 패턴은 같은 Zone으로 이어집니다.

### 러닝 중 잡음 처리

전처리(직류 제거) → 대역 필터(Web Audio biquad 하이패스 100Hz/로우패스 1200Hz, 초기 설정값) → smoothing/envelope(노이즈 플로어 EMA) → 이벤트 검출 → 이벤트 간 간격 → 호흡수 순서로 처리합니다. 그 과정에서 다음을 휴리스틱으로 분류해 호흡으로 세지 않거나 신호 품질을 낮춥니다 (`classifyArtifact()`): 발소리, 케이블/옷 마찰, 바람 소리, 말소리, 주변 소음, 마이크 clipping. **이 분류 기준(배율, 문턱값)은 논문에서 검증된 값이 아니라 이 앱이 직접 설계한 초기 구현값이며, 실제 사용자 녹음으로 검증이 필요합니다.**

### 가속도계(움직임 센서) 사용과 한계

가능하면 `DeviceMotionEvent`로 움직임 크기를 측정해 발소리/충격이 큰 구간에서는 호흡 이벤트를 확정하지 않고 신호 품질을 낮춥니다. 다만:

- iOS 13 이상은 사용자 제스처로 명시적 권한 요청이 필요합니다(`ensureMotionPermission()`).
- 사용자가 권한을 거부하거나, 브라우저/기기가 `DeviceMotionEvent`를 지원하지 않으면 이 앱은 **오디오 신호만으로 만든 휴리스틱(진폭 급변 + 낮은 zero-crossing rate)** 으로 발소리 등을 추정합니다. 이 경우 발소리·충격음 오검출 가능성이 가속도계를 쓸 때보다 높습니다.
- 가속도계 유무와 무관하게, 이 앱은 실제 임상 검증된 움직임 아티팩트 판별 알고리즘을 쓰지 않습니다 (아래 "연구 근거" 참고).

### 신호 품질 점수와 상태

`computeQualityScore()`가 신호 대 잡음비, 유효 호흡 이벤트 비율, 호흡 주기 규칙성, 최근 데이터 갱신 여부, clipping 비율, 움직임/충격음 비율, 장치 보정 상태를 가중합산해 0~100점을 냅니다. 가중치는 이 앱이 직접 정한 값이며 실제 데이터로 검증되지 않았습니다. 이 점수와 몇 가지 개별 조건(`deriveStatus()`)으로 아래 7가지 상태 중 하나를 화면에 표시합니다: 보정 중 / 측정 중 / 신호 양호 / 신호 불안정 / 주변 소음이 큼 / 마이크 위치 확인 필요 / 측정 불가.

### Zone/강도는 언제만 표시되나

`canDisplayZone()`은 상태가 "신호 양호"이고 확정된 호흡 이벤트가 3회 이상일 때만 `true`를 반환합니다. 앱을 처음 열었을 때, 그리고 신호 품질이 나빠질 때마다 화면의 BPM/Zone은 **강제로 표시하지 않고 `null`(빈 값)로 돌아갑니다** - 신호 품질 배지와 안내 문구로 이유를 보여줍니다.

**수정된 버그 (줄 이어폰 등에서 BPM이 계속 안 나오던 문제)**: 초기 구현에는 "호흡이 불규칙한가?"를 판단하는 로직이 "판단할 데이터가 충분한가?"를 확인하기 전에 실행되는 순서 버그가 있었습니다. 확정된 호흡이 2회 이하일 때는 규칙성(변동계수)을 계산할 표본 자체가 부족한데도 최악값으로 취급해버려서, 정상적으로 숨을 쉬어도 "신호 불안정" 상태에 영구히 갇혀 BPM/Zone이 절대 뜨지 않는 경우가 있었습니다. 성인 안정 시 호흡은 분당 12~20회(주기 3~5초)이고 호흡 간격은 원래 ±15~20% 정도 자연스럽게 변동하므로, 이 변동성을 표본이 적은 상태에서 "불안정"으로 오판하지 않도록 (1) 데이터 충분성 확인을 먼저 하도록 순서를 바꾸고, (2) 규칙성 판단에 더 많은 표본(최근 8개 간격)을 쓰도록 고쳤습니다. 같은 이유로, 신호 대 잡음비 추정도 5초 보정 한 번의 스냅샷에 영구히 묶이지 않고 실제 확정된 호흡이 쌓이면 그 값으로 갱신되도록 했고, "움직임이 조금만 있어도 호흡 확정을 막던" 로직도 실제 동작(걷기/팔 흔들림)까지 막아버리던 부분을 완화했습니다. `tests/breathing-engine.tests.core.js`의 "회귀 테스트" 항목이 이 문제를 재현/검증합니다.

**추가로 수정한 문제 (고정된 감지 임계값)**: `peakThresholdMultiplier`(예: 줄 이어폰 1.6배)는 검증되지 않은 초기 추정값인데, 이 값이 고정되어 있으면 실제 사용자의 호흡 신호가 우연히 그보다 살짝 낮을 경우 아무리 기다려도 단 한 번도 호흡이 확정되지 않는 구조적 문제가 있었습니다. 이를 표준적인 피크 검출 기법인 **점진적 임계값 완화**로 고쳤습니다: 마지막 확정된 호흡(또는 세션 시작) 이후 일정 시간(10초)이 지나도 다음 호흡이 확정되지 않으면, 임계값을 서서히 낮춰(최대 30초에 걸쳐 최소 배율 1.25배까지) 처음에 너무 엄격하게 잡힌 임계값 때문에 영원히 감지되지 않는 상황을 막습니다. 단, 순수 주변 소음만 있는 경우(호흡 없음)에는 완화 후에도 절대 오검출되지 않도록 최소 배율에 안전 여유를 두고 별도로 검증했습니다 (`tests/breathing-engine.tests.core.js`의 "1c) 회귀 테스트"와 "9) 호흡 없이 주변 소리만 있는 경우" - 후자는 45초, 즉 완화가 완전히 진행된 뒤까지 포함해 테스트합니다).

**진단 도구**: 운동 화면의 호흡 측정 패널에 "상세 신호 정보 보기"를 누르면 현재 정규화된 신호 레벨, 현재 감지 임계값, 이번 프레임이 호흡으로 확정됐는지/어떤 아티팩트로 분류됐는지, 보정값(주변 소음, 호흡 이벤트 평균 크기, 정규화 배율, clipping 비율)을 실시간으로 볼 수 있습니다. 그래도 숫자가 안 뜨는 경우, 이 정보를 캡처해서 공유하면 원인을 훨씬 빠르게 좁힐 수 있습니다.

### 호흡 메트로놈 (페이싱 보조 기능)

운동 화면의 "호흡 메트로놈 사용" 체크박스를 켜면, 화면의 원이 설정한 속도(분당 8~20회, 기본 12회)로 커지고("들이쉬기")/작아지며("내쉬기") 일정한 호흡 리듬을 유지하도록 도와줍니다. 원하면 부드러운 알림음(들이쉬기=높은 음, 내쉬기=낮은 음, Web Audio로 즉석 생성 - 별도 음원 파일 없음)도 함께 켤 수 있습니다.

**중요: 이 메트로놈은 순수한 페이싱 보조 도구이며, 실제 감지/계산 파이프라인(`BreathingEngine`)에는 전혀 연결되어 있지 않습니다.** 언제든 켜고 끄거나 속도를 바꿔도 측정 중인 호흡수·신호 품질·Zone 계산에는 영향을 주지 않습니다 - 다만 사용자가 실제로 더 규칙적인 리듬으로 숨을 쉬게 되면, 그 결과로 호흡 간격의 변동계수(intervalCv)가 자연스럽게 낮아져 신호 품질 점수의 규칙성 항목에 간접적으로 도움이 될 수는 있습니다.

**소리는 기본적으로 꺼져 있습니다.** 스피커나 이어폰으로 재생되는 알림음은 바로 그 알림음을 듣고 있는 마이크에도 함께 들어갈 수 있고, `classifyArtifact()`가 이를 케이블/충격음 등으로 분류해 신호 품질에 영향을 줄 가능성이 있기 때문입니다 (실제로 걸러질지는 소리 크기·기기·판별 임계값에 따라 다르며, 이 앱이 이 상호작용을 별도로 검증하지는 않았습니다). 소리 없이 화면만으로도 리듬을 맞출 수 있으므로, 필요할 때만 소리를 켜는 것을 권장합니다.

속도·소리 설정은 `state.settings`(IndexedDB)에 저장되어 다음 방문에도 유지되며, 서버로는 전송되지 않습니다.

**소리가 안 들리는 경우**: 먼저 설정 카드의 **"🔊 소리 테스트"** 버튼을 눌러보세요 - 이 버튼은 운동을 시작하지 않고도, 마이크 세션과 무관한 별도의 `AudioContext`로 즉시 알림음을 재생해봅니다. 여기서도 안 들리면 기기 음량/무음 모드/브라우저 자체 문제일 가능성이 높고, 여기서는 들리는데 실제 측정 중에는 안 들린다면 아래 알려진 제약 때문일 수 있습니다.

- **수정한 버그**: 이전 버전은 세션 시작 시 한 번만 `AudioContext.resume()`을 호출했습니다. 브라우저가 세션 도중(탭이 백그라운드로 가거나 OS 절전 등으로) 오디오 컨텍스트를 다시 suspended 상태로 되돌리면, 그 뒤로는 알림음이 예외 없이 조용히 재생되지 않는 상태가 세션 끝까지 이어질 수 있었습니다. 이제 매 틱마다 컨텍스트 상태를 확인하고 필요하면 다시 resume()하도록 고쳤고, 소리 자체도 더 크고(피크 게인 0.12→0.35) 길게(180ms→260ms) 조정했습니다.
- **알려진 플랫폼 제약 (완전히 고칠 수 없음)**: 일부 모바일 브라우저는 `getUserMedia()`로 마이크가 켜져 있는 동안 그 페이지의 오디오 출력 전체를 통화용 경로(모노, 저음량, 때로는 이어폰 대신 기기 자체 리시버)로 바꿉니다. 웹 페이지에는 이 출력 경로를 직접 지정할 수 있는 표준 방법이 없어 코드로 완전히 해결할 수 없습니다. 이 앱은 마이크 요청 시 `echoCancellation`을 이미 꺼둬(가장 흔한 유발 요인) 이 문제를 어느 정도 완화하지만, 모든 기기에서 확실히 피할 수 있다고 보장하지는 않습니다.

### 표현에 대한 원칙

이 앱은 실제 심박수 센서로 검증하기 전까지 "정확한 심박수"나 "정확한 Zone"이라고 표현하지 않습니다. 화면에는 항상 "호흡 기반 호흡수 추정", "호흡 기반 강도 추정", "Zone 2/3 추정" 처럼 추정치임을 표기합니다.

### 검증 모드 (개발자용)

내 프로필 화면 하단 "검증 모드"에서 `{predictedBpm, referenceBpm, activity, deviceType, quality}` 배열 형태의 JSON 파일을 불러오면 `BreathingEngine.computeValidationReport()`가 전체/활동별(정지·걷기·러닝)/장치 유형별/신호 품질별로 MAE, RMSE, 평균 편향, 95% 일치 한계(Bland-Altman 95% limits of agreement)를 계산해 보여줍니다. `predictedBpm`은 이 앱이 추정한 값, `referenceBpm`은 테스터가 별도의 기준 센서(가슴 스트랩형 호흡/심박 센서 등)로 동시에 측정한 값이어야 합니다 - **이 앱 자체에는 기준 센서 연동 기능이 없으므로, 이 리포트의 신뢰도는 전적으로 테스터가 입력하는 데이터의 품질에 달려 있습니다.** `tests/sample-validation-data.json`은 파일 형식을 보여주기 위한 **합성(가짜) 예시 데이터**이며 실제 측정값이 아닙니다.

### 테스트 실행

Node이 설치되어 있다면:

```bash
npm test
```

Node이 없다면 `tests/run-tests.html`을 아무 브라우저로 열어도 같은 테스트가 그대로 돌아갑니다(콘솔과 화면에 결과가 출력됩니다). 테스트는 합성 신호(seeded PRNG로 생성)로 다음을 확인합니다: 줄 이어폰 근접/원거리, 무선 이어폰, 헤드셋, 러닝 중 마이크 위치 변화, 발소리 증가, 바람 소리 증가, 케이블 흔들림, 호흡 없이 주변 소리만 있는 경우, 신호가 5초 이상 끊기는 경우, Zone 표시 게이팅, 검증 통계 계산. **이 테스트들은 코드가 의도한 대로 동작하는지 확인하는 것이지, 실제 사용자에게 정확하다는 증거가 아닙니다** - 그 증거는 위 "검증 모드"로 실측 데이터를 넣어야 나옵니다.

### 연구 근거와 한계 (그대로 인용 - 검증 필요 표시 포함)

- **RespEar**: 이어폰 마이크 기반 호흡수 추정은 가능하지만, 활동 중 발소리와 움직임으로 오차가 증가할 수 있다고 보고합니다. 이 앱의 발소리/움직임 아티팩트 처리(`classifyArtifact()`, 가속도계 게이팅)는 이 문제의식에 대응하려는 시도이며, RespEar 자체의 알고리즘을 그대로 구현한 것은 아닙니다.
- **EarResp-ANS**: 이어폰 기반 호흡 측정에는 적응형 소음 억제와 이상값 제거가 필요하다고 지적합니다. 이 앱의 비대칭 노이즈 플로어 추적과 이상값(발소리/바람/케이블/말소리/clipping) 분류가 그 역할을 하도록 설계했지만, 정식으로 같은 방법론을 따른 것은 아니며 별도 검증이 필요합니다.
- **웨어러블 생체신호 연구 전반**: 움직임 아티팩트 처리와 신호 품질 평가가 필수적이라는 공통된 결론을 따라, 이 앱도 움직임 기반 게이팅과 신호 품질 점수를 두었습니다.
- 위 세 참고문헌은 "이런 문제가 있고 이런 방향의 해법이 필요하다"는 근거로만 인용했습니다. **이 앱의 구체적인 임계값·가중치·거리 프로필 수치는 어느 논문에서도 직접 검증된 값이 아니라, 초기 구현값이며 실제 사용자 데이터로 검증해야 하는 값입니다.** (호흡수→Zone 환산식 자체의 출처는 `index.html`의 `estimateZoneAndBpmFromBreathing()` 주변 주석에 있는 별도 문헌을 참고하세요 - 이 섹션과는 다른 근거입니다.)

## GEMINI_API_KEY / NUTRITION_API_KEY는 어디에 넣나요?

**코드 어디에도 넣지 마세요.** Vercel 프로젝트의 **Settings → Environment Variables**에만 각각의 이름으로 등록합니다.

- `GEMINI_API_KEY` → `api/analyze-food.js`가 `process.env.GEMINI_API_KEY`로 읽습니다 (음식 사진 분석용).
- `NUTRITION_API_KEY` → `api/nutrition-info.js`가 `process.env.NUTRITION_API_KEY`로 읽습니다 (음식 이름으로 영양정보 조회용).

두 값 모두 서버 쪽 실행 환경에만 존재하고, 브라우저로는 절대 전달되지 않습니다.
